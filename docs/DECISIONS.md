2026-09-16 3D 첫 성공(M4 Max 36GB, Metal 텍스처 가속 없음, pipeline 512, 텍스처 1024,
면 상한 3만): 컨셉 이미지 466.69초·28.7GB, 배경 제거 4.89초·5.0GB, TRELLIS.2
557.02초·18.8GB(정점 187만·삼각형 377만, KDTree 방식 굽기 173초), Blender 정리
1.62초·0.5GB(19만 9946 → 2만 9998면, 1.00×0.74×0.74m, 텍스처 2장), gltfpack
0.13초(6.19MB → 4.66MB). 소품 하나에 약 17분이다. 메모리는 TRELLIS보다 이미지 모델이
더 쓰므로, 3D의 병목은 메모리가 아니라 시간이다. Metal 가속을 켜면 굽기 시간이 줄 여지가 있다.

2026-09-16 텍스처 품질 판정: 위 결과를 Cycles로 렌더하니 표면 전체에 잡티가 깔렸다.
감축 전 `raw.glb`(19만 9946면, 원본 UV)를 같은 각도로 렌더해도 똑같았으므로 원인은
Blender 감축이 아니라 굽기다. Xcode가 없어 Metal 래스터라이저 대신 KDTree 대체 경로로
구운 결과다(굽기 173초). 따라서 Metal 텍스처 가속은 속도 선택지가 아니라 품질 전제
조건으로 다루고, 진단에 "3D 텍스처 품질" 항목을 따로 두었다. Metal 설치 후 같은 입력·
시드로 다시 만들어 비교 기록을 남긴다.

2026-09-16 해상도 실험: 텍스처 잡티가 복셀 격자(512³)의 성김 때문인지 보려고 같은 컨셉
이미지·같은 시드로 `pipelineType: 1024`를 돌렸다. 33분(1988초) 뒤 최대 50.3GB에서 macOS가
프로세스를 종료했다. 36GB에서 1024는 쓸 수 없다. 512는 18.8GB로 안정적이므로 기본값을
유지하고, 텍스처 품질은 해상도가 아니라 Metal 굽기로 해결한다. 이 수치가 더 큰 통합
메모리가 필요한 첫 구체적 근거다.

2026-09-16 Metal 없이 굽기 수정: 회사 기기라 Xcode를 설치할 수 없어 대체 경로 자체를
고쳤다. 색 채우기를 교체해(이웃 6개·2.5배 범위·거리 제곱 반비례, 구멍은 가장 가까운 유효
텍셀 복사) 같은 컨셉 이미지·시드로 다시 만들고 같은 조명으로 렌더해 비교했다. 검은 잡티가
사라졌고, 아틀라스 기준 거의 검은 픽셀 0%, 평균 밝기 0.522 → 0.635, 채도는 0.205로 같다.
UV 섬 안 텍셀은 100% 실제 색을 받는다. 탐색 범위를 4배 → 2.5배로 좁힌 것은 결과에 차이를
만들지 않았다. 이미 모든 텍셀이 가까운 복셀을 찾고 있었기 때문이다. 남은 얼룩은 512³
복셀에서 재질 경계가 섞이는 한계이므로 Metal이 있으면 더 나아질 여지는 남는다.

설치는 커밋으로 고정한다: trellis-mac `d58628f4`, trellis2-apple `17347247`, TRELLIS.2
`75fbf018`, mtlbvh `6b2a0f63`, mtldiffrast `c9499ba2`, mtlgemm `566c1337`, mtlmesh
`7de3864f`, utils3d `9a4eb15e`. 모두 저장소 LICENSE가 MIT다(2026-09-16 확인). o-voxel은
PyTorch 2.14가 C++20을 요구해 빌드 플래그만 바꿨다.

### DINOv3 확인 보완 (2026-09-22)

[사용 중인 모델의 LICENSE.md](https://huggingface.co/facebook/dinov3-vitl16-pretrain-lvd1689m/blob/main/LICENSE.md)
원문(2025-08-19 갱신)을 확인했다. 1.a는 전 세계·무상 사용/복제/수정/배포 권리를 부여하며 비상업 한정이나
한국 제외 문구가 없다. 1.b.i는 DINO Materials 또는 그 파생물을 배포할 때 동일 계약 적용과 계약 사본 제공,
1.b.ii는 연구 결과 출판 시 DINO 사용 인정을 요구한다. 일반 제품/출력에 “Built with DINOv3”를 붙여야 한다는
문구는 없다. 이전 SETUP의 미확인 보고를 정정한다. 1.b.iii~v의 법률·개인정보·무역통제·금지 최종 용도와
역공학 관련 제한은 계속 적용한다. 가중치를 앱과 함께 배포할 때에는 계약 사본을 포함한다.

## 2D 이미지 모델

### 실사·애니 카테고리와 모델 선택 (2026-09-22)

실사·애니를 게임 아이콘 프롬프트로 처리하면 흰 배경·중앙 물체·배경 제거 지시가 충돌한다. 카테고리와
전용 종류 프리셋을 추가하고 배경을 보존한다. 카테고리와 가중치는 일대일 관계가 아니므로 기존 범용 모델을
기본으로 두고, 이미 설치된 Z-Image Turbo를 작업별 비교 선택지로 노출한다. 애니 특화 체크포인트나 LoRA는
이번에 채택하지 않았다. 특정 화풍의 일관성이 더 필요하면 해당 가중치의 라이선스·Mac 실행·동일 입력 비교를
별도로 검증한다. 기존 게임/3D 기본 모델·스텝·양자화·해상도는 바꾸지 않는다.

라이선스 원문 재확인(2026-09-22):
[FLUX.2 klein 4B LICENSE](https://huggingface.co/black-forest-labs/FLUX.2-klein-4B/blob/main/LICENSE.md),
[Z-Image 공식 LICENSE](https://github.com/Tongyi-MAI/Z-Image/blob/main/LICENSE),
[Z-Image Turbo 모델 카드](https://huggingface.co/Tongyi-MAI/Z-Image-Turbo).
두 모델은 Apache-2.0이며 전 세계 사용·판매 관련 권리를 허용하고 한국 제외 조항이 없다. 재배포 시
라이선스·저작권/NOTICE 유지와 수정 고지를 지킨다. FLUX 9B의 별도 라이선스는 이 선택지에 포함하지 않는다.

실행 검증: 같은 주제(파란 재킷·짧은 검은 머리의 성인 여성이 오후 야외 카페에 앉아 있음), 시드 42,
768×1024, 8비트, MLX 캐시 8GB, 배경 포함. 실사 두 모델은 **완전히 같은 프롬프트**를 사용했다.
애니는 같은 주제에 애니 프리셋을 적용한 기능 검증이며 실사와 같은 프롬프트라는 뜻은 아니다.

없었다. mflux sidecar의 실제 모델 저장소·스텝·양자화도 기록과 일치했다. 실사 두 결과 모두 사진 스타일,
애니 결과는 선화·셀 채색으로 나왔다. FLUX 실사는 지시한 따뜻한 오후 조명이 더 뚜렷했다. 한 장씩의 사례이므로
일반적인 품질 순위나 화풍 일관성을 입증하지는 않는다. Z 실행 중 시스템 스왑 약 16GiB가 관찰됐으나 다른 앱도
포함한 전체 수치여서 모델 단독 사용량으로 해석하지 않는다. 추가 Z 애니 비교는 중지했고 기본값 변경은 없다.
원본 그림·메타데이터·측정과 비교 보고서는 `output/diagnostics/image-categories/REPORT.md`에서 확인한다.

2026-09-16 첫 측정(M4 Max 36GB, 1024×1024, 9스텝, bf16, 양자화 없음): 후보 2장에
1148초, 생성 단계 최대 메모리 37.75GB(mflux가 보고한 MLX 최대 37.93GB)로 통합 메모리
36GB를 넘겨 스왑이 일어났다. 그래서 `config/presets.json`의 기본값에 `quantize: 8`을
넣었다. 양자화 없이 쓰려면 더 큰 메모리가 필요하다. 이 수치는 장비 교체 판단의 첫 근거다.

같은 날 8비트로 다시 측정(같은 프롬프트·시드, 후보 2장): 생성 413.65초·최대 32.9GB,
배경 제거 5.02초·5.0GB, 정리 0.07초로 2D 전체가 처음 끝까지 성공했다. 양자화로 시간은

### 편집 레이어·영역·보관 정리 (2026-09-17 오전)

사용자 검토: 색 교체가 고른 색을 에셋 전체에서 바꾸고 로고가 하나뿐이라, 상자가 아닌 물체나 자물쇠 같은 작은
부위를 원하는 대로 꾸밀 수 없었다. 보관함의 승인·거절은 다음 동작에 쓰이지 않아 의미가 없다는 지적도 받았다.

- 편집 설정을 레이어 목록으로 바꾼다. 색 레이어에 브러시 영역을 두어 같은 색이 여러 부위에 있어도 칠한 곳만 바꾼다.
  부위를 자동으로 나누는 분할 모델(SAM 계열 등)은 새 모델·라이선스 검토가 필요해 이번에는 넣지 않았다.
  브러시는 모델 없이 정확하고, 나중에 자동 분할이 들어와도 같은 `region` 자리에 마스크를 채우면 된다.
- 3D 로고의 기본을 "이어진 표면만"으로 바꾼다. 평면 투영의 깊이 범위만으로는 튀어나온 자물쇠에 붙인 로고가 뒤
  판에도 찍혔다. 이음매 정점을 위치로 병합해 면을 이어 찾고, 로고 방향을 보지 않는 옆면에서 멈춘다. 예전 편집본은
  결과가 바뀌지 않도록 `projection`으로 옮긴다. 곡면을 따라 늘여 감싸는 방식은 왜곡 보정 설계가 따로 필요해 보류한다.
- 이미지·3D의 승인·거절 UI를 없애고 즐겨찾기·컬렉션·태그·메모로 바꾼다. 3D 변환·편집·프리비즈가 승인을 요구하지
  않았기 때문이다. `review` 필드와 API, 프리비즈 컷 승인은 유지한다(컷 확정에 쓰인다). 자동 검사는 여전히 아무것도 고르지 않는다.
- 중간 파일 정리는 삭제가 아니라 macOS 휴지통으로 옮기고, main이 엔진의 분류를 다시 읽어 `intermediate`만 받는다.
  `mesh/source.npz`·입력 이미지·편집 기준처럼 다시 만들기에 필요한 파일은 대상이 아니다.
- 새 패키지·모델은 없다. 알림은 Electron 기본 Notification, 휴지통은 `shell.trashItem`을 쓴다.

LOCK 문구를 이어진 표면으로 붙여 저장했다. 저장 2.78초(최대 0.50GB), 검수 3.65초이며 Blender 렌더가 미리보기와
같았다. 예전 형식 편집본은 두 레이어로 열려 같은 모습이었다.

### 설명 중심 시작 흐름 (2026-09-22)

알린다. 대상을 찾지 못하거나 수량·길이·제외 표현이 지원 범위를 벗어나면 임의의 예시 장면으로 대체하지 않는다.

EEVEE에서 생성 메시가 속이 비어 보이는 문제는 재질 설정이었다. glTF가 단면 재질에
`use_backface_culling`을 켜는데 TRELLIS 메시는 면 방향이 고르지 않아 표면 대부분이 잘렸다.
도구가 이 값을 끄고, 반사를 계산하지 않는 스케치 렌더에서 하늘만 비춰 유리처럼 보이는
ORM 금속성도 함께 끈다. 이 두 가지는 취향이 아니라 스케치가 형태를 잘못 보여 주는 문제다.

Blender 5.2에서 컴포지터가 노드 그룹(`scene.compositing_node_group`)으로 바뀌었고
`CompositorNodeComposite`·`file_slots`·`CompositorNodeMapRange`가 없어졌다. File Output 노드는
멀티레이어 EXR로만 써져서(프레임당 8MB) 색·깊이·윤곽을 한 번의 렌더로 PNG로 받을 수 없다.
그래서 그룹 출력을 바꿔 가며 출력마다 렌더를 호출한다. EEVEE에서 한 장이 0.1초라 이 방식이
EXR을 쓰고 다시 변환하는 것보다 싸고 결과가 예측 가능하다. 동영상은
`image_settings.media_type = "VIDEO"`로 바꿔야 FFMPEG(H.264)를 고를 수 있다.

| LTX-Video 계열 | 보류 | "LTX-Video Open Weights License"라는 자체 라이선스다. 매출 조건이 붙는다는 설명이 2차 자료에 있으나 원문을 확인하지 않았다. Stability 계열을 보류한 것과 같은 이유다 |
| HunyuanVideo 계열 | 기각 | Hunyuan 계열 적용 지역 규칙을 그대로 적용한다(위 3D 항목) |
| 유료 MCP(Higgsfield 등) | 기본 경로 아님 | 비용 때문에 이 저장소를 만들었다. 이 세션에서도 연결하지 않았다 |
