2026-09-16 3D 첫 성공(M4 Max 36GB, Metal 텍스처 가속 없음, pipeline 512, 텍스처 1024,
면 상한 3만): 컨셉 이미지 466.69초·28.7GB, 배경 제거 4.89초·5.0GB, TRELLIS.2
557.02초·18.8GB(정점 187만·삼각형 377만, KDTree 방식 굽기 173초), Blender 정리
1.62초·0.5GB(19만 9946 → 2만 9998면, 1.00×0.74×0.74m, 텍스처 2장), gltfpack
0.13초(6.19MB → 4.66MB). 소품 하나에 약 17분이다. 메모리는 TRELLIS보다 이미지 모델이
더 쓰므로, 3D의 병목은 메모리가 아니라 시간이다. Metal 가속을 켜면 굽기 시간이 줄 여지가 있다.

2026-09-16 텍스처 품질 판정: 위 결과를 Cycles로 렌더하니 표면 전체에 잡티가 깔렸다.
감축 전 `raw.glb`(19만 9946면, 원본 UV)를 같은 각도로 렌더해도 똑같았으므로 원인은
Blender 감축이 아니라 굽기다. Xcode가 없어 Metal 래스터라이저 대신 KDTree 대체 경로로
구운 결과다(굽기 173초). 따라서 Metal 텍스처 가속은 속도 선택지가 아니라 품질 전제
조건으로 다루고, 진단에 "3D 텍스처 품질" 항목을 따로 두었다. Metal 설치 후 같은 입력·
시드로 다시 만들어 비교 기록을 남긴다.

2026-09-16 해상도 실험: 텍스처 잡티가 복셀 격자(512³)의 성김 때문인지 보려고 같은 컨셉
이미지·같은 시드로 `pipelineType: 1024`를 돌렸다. 33분(1988초) 뒤 최대 50.3GB에서 macOS가
프로세스를 종료했다. 36GB에서 1024는 쓸 수 없다. 512는 18.8GB로 안정적이므로 기본값을
유지하고, 텍스처 품질은 해상도가 아니라 Metal 굽기로 해결한다. 이 수치가 더 큰 통합
메모리가 필요한 첫 구체적 근거다.

2026-09-16 Metal 없이 굽기 수정: 회사 기기라 Xcode를 설치할 수 없어 대체 경로 자체를
고쳤다. 색 채우기를 교체해(이웃 6개·2.5배 범위·거리 제곱 반비례, 구멍은 가장 가까운 유효
텍셀 복사) 같은 컨셉 이미지·시드로 다시 만들고 같은 조명으로 렌더해 비교했다. 검은 잡티가
사라졌고, 아틀라스 기준 거의 검은 픽셀 0%, 평균 밝기 0.522 → 0.635, 채도는 0.205로 같다.
UV 섬 안 텍셀은 100% 실제 색을 받는다. 탐색 범위를 4배 → 2.5배로 좁힌 것은 결과에 차이를
만들지 않았다. 이미 모든 텍셀이 가까운 복셀을 찾고 있었기 때문이다. 남은 얼룩은 512³
복셀에서 재질 경계가 섞이는 한계이므로 Metal이 있으면 더 나아질 여지는 남는다.

설치는 커밋으로 고정한다: trellis-mac `d58628f4`, trellis2-apple `17347247`, TRELLIS.2
`75fbf018`, mtlbvh `6b2a0f63`, mtldiffrast `c9499ba2`, mtlgemm `566c1337`, mtlmesh
`7de3864f`, utils3d `9a4eb15e`. 모두 저장소 LICENSE가 MIT다(2026-09-16 확인). o-voxel은
PyTorch 2.14가 C++20을 요구해 빌드 플래그만 바꿨다.

2026-09-16 첫 측정(M4 Max 36GB, 1024×1024, 9스텝, bf16, 양자화 없음): 후보 2장에
1148초, 생성 단계 최대 메모리 37.75GB(mflux가 보고한 MLX 최대 37.93GB)로 통합 메모리
36GB를 넘겨 스왑이 일어났다. 그래서 `config/presets.json`의 기본값에 `quantize: 8`을
넣었다. 양자화 없이 쓰려면 더 큰 메모리가 필요하다. 이 수치는 장비 교체 판단의 첫 근거다.

같은 날 8비트로 다시 측정(같은 프롬프트·시드, 후보 2장): 생성 413.65초·최대 32.9GB,
배경 제거 5.02초·5.0GB, 정리 0.07초로 2D 전체가 처음 끝까지 성공했다. 양자화로 시간은
2.8배 줄고 최대 메모리는 4.9GB 낮아졌다. 그래도 36GB 중 32.9GB라 Chrome·VS Code를 함께
쓰는 이 기기에서는 여유가 없어 `mlxCacheLimitGb: 8`을 기본값에 더했다.

2026-09-16 같은 조건 비교(아이템 아이콘 프리셋, 같은 프롬프트·시드 7·8, 1024×1024, 8비트):
Z-Image Turbo는 생성 413.65초·최대 32.9GB, FLUX.2 klein 4B는 41.99초·22.7GB였다. 약 10배
빠르고 메모리는 10GB 낮다. 프롬프트 반영도 klein이 나았다. 같은 "코르크 마개" 지시에서
Z-Image는 병과 같은 붉은색으로 그렸고 klein은 코르크 재질로 그렸다. 그래서 기본 모델을
klein 4B로 바꿨다. Z-Image Turbo 가중치는 이미 받아 두었으므로 되돌릴 때는
`config/presets.json`의 `imageModel` 한 곳만 고치면 된다.

2026-09-16 모델 교체 후 3D 전체 실행(같은 상자 주제, pipeline 512, 면 상한 3만):
컨셉 25.05초·20.7GB, 배경 제거 5.26초, TRELLIS 977.27초·24.3GB, 정리 1.77초, 최적화 0.13초로
전체 16.8분이었다. 이미지 단계는 466.7초 → 25.05초로 19배 빨라졌지만 3D 단계는 557초 →
977초로 느려졌다. klein의 컨셉이 더 선명해 TRELLIS가 디테일을 형태로 해석했기 때문이다
(정점 187만 → 410만, 삼각형 377만 → 829만). 그 메시를 3만 면으로 줄이니 표면이 거칠어져,
렌더 품질은 이전 컨셉보다 나빴다.

교훈: 3D용 컨셉 이미지는 선명할수록 좋은 것이 아니다. 매끈하고 단순한 형태로 유도하거나
면 상한을 올려야 한다. 다음 실험 후보는 (1) `prop-3d` 프롬프트에 매끈한 표면·단순한 형태
지시 추가, (2) 면 상한 3만 → 10만이다. 한 번 확인에 약 17분이 든다.

2026-09-16 면 상한 검증: 같은 원본 메시를 3만 면과 10만 면으로 각각 뽑아 같은 조명으로
렌더해 비교했다. 실루엣만 조금 매끄러워지고 표면의 얼룩은 그대로였으며 파일은 5.4MB →
13MB로 커졌다. 거칠게 보이는 원인은 형태가 아니라 텍스처다. 기본값 3만 면을 유지한다.
면 줄이기는 Blender 단계(약 2초)라 TRELLIS를 다시 돌리지 않고 검증할 수 있다.

2026-09-16 컨셉 프롬프트 실험: `prop-3d` 프롬프트에 매끈한 표면·단순한 형태·질감 최소화를
넣고 같은 주제·같은 시드로 다시 만들었다. 메시가 정점 410만 → 329만, 삼각형 829만 → 669만으로
덜 조밀해졌고 텍스처는 5.4MB → 4.0MB로 줄었다. 렌더에서 실루엣이 매끄러워지고 널·띠·걸쇠
구조가 뚜렷해져 프롬프트를 채택한다. 전체 시간은 16.3분으로 비슷하다.

다만 표면의 색 얼룩은 그대로다. 이것은 512³ 복셀에서 색을 읽는 한계이고, 1024는 이 기기에서
메모리 초과로 불가능하다. 지금 수준은 스타일라이즈드 소품에는 쓸 만하고, 사실적인 질감이
필요하면 GLB의 UV를 그대로 두고 Blender에서 직접 칠하거나 Metal 굽기·더 큰 메모리를 기다려야
한다. 오늘 기준 3D 품질의 남은 병목은 굽기 코드가 아니라 복셀 해상도다.

| 2026-09-16 | 스케치 렌더러는 **EEVEE**. 아래 실측에서 Workbench와 비용이 같은 자리인데 그림자와 1m 격자 바닥이 나온다. Workbench는 절차적 텍스처를 그리지 않아 바닥이 평평한 회색이 되고, 카메라가 움직여도 화면이 거의 변하지 않아 이동을 판단할 수 없다 |
| 2026-09-16 | Cycles는 프리비즈에서 쓰지 않는다. 같은 계획에 7배 시간·4배 메모리를 쓰고 판단은 달라지지 않는다 |
| 2026-09-16 | 산출물은 정지 스토리보드가 아니라 **애니매틱**(샷별 mp4)이다. 프레임이 싸서 6컷 15초 트레일러가 19.5초에 끝난다. 트레일러 프리비즈에서 확인할 것이 카메라 움직임이므로 정지 프레임만으로는 목적을 못 채운다. 깊이·윤곽은 처음·중간·끝 프레임만 남겨 비용을 낮춘다(`aux: "all"`로 전 프레임 가능) |
| 2026-09-16 | 기본을 점토(clay) 재질로 둔다. 같은 샷을 텍스처와 점토로 비교하니 점토가 형태·접지·구도를 더 잘 보여 주고, 지금 텍스처는 복셀 한계로 얼룩이 있어 판단을 방해한다. 텍스처가 필요하면 `clay: false`로 켠다 |

2026-09-16 렌더러 실측(M4 Max 36GB, 같은 2샷 계획, 960×540, 점토, 샷마다 24프레임
애니매틱 + 대표 프레임 3장 + 깊이·윤곽 6장, 프로세스 전체를 `/usr/bin/time -l`로 측정):
Workbench 2.95초·1.09GB, EEVEE 6.00초·2.10GB, Cycles(Metal GPU, 16샘플) 43.35초·9.06GB.
EEVEE는 첫 프레임에 셰이더 컴파일로 약 2초를 쓰고 이후 출력 한 장에 약 0.1초다.
6컷 트레일러 전체(180프레임 애니매틱 + 대표 18장 + 보조 36장)는 19.5초·2.09GB·17MB였다.
3D 소품 하나가 약 17분인 것과 비교하면 연출을 먼저 확정할 여유가 충분하다.

EEVEE에서 생성 메시가 속이 비어 보이는 문제는 재질 설정이었다. glTF가 단면 재질에
`use_backface_culling`을 켜는데 TRELLIS 메시는 면 방향이 고르지 않아 표면 대부분이 잘렸다.
도구가 이 값을 끄고, 반사를 계산하지 않는 스케치 렌더에서 하늘만 비춰 유리처럼 보이는
ORM 금속성도 함께 끈다. 이 두 가지는 취향이 아니라 스케치가 형태를 잘못 보여 주는 문제다.

Blender 5.2에서 컴포지터가 노드 그룹(`scene.compositing_node_group`)으로 바뀌었고
`CompositorNodeComposite`·`file_slots`·`CompositorNodeMapRange`가 없어졌다. File Output 노드는
멀티레이어 EXR로만 써져서(프레임당 8MB) 색·깊이·윤곽을 한 번의 렌더로 PNG로 받을 수 없다.
그래서 그룹 출력을 바꿔 가며 출력마다 렌더를 호출한다. EEVEE에서 한 장이 0.1초라 이 방식이
EXR을 쓰고 다시 변환하는 것보다 싸고 결과가 예측 가능하다. 동영상은
`image_settings.media_type = "VIDEO"`로 바꿔야 FFMPEG(H.264)를 고를 수 있다.

### 최종 영상 경로

2026-09-16 조사 기준: 로컬 오픈웨이트로 가고 유료 MCP(Higgsfield 등)는 기본 경로로 쓰지 않는다.
프리비즈 샷 값이 쌓인 뒤 별도로 측정·검증한다.

| 모델·도구 | 판정 | 근거 |
| --- | --- | --- |
| Wan 2.2 (`Wan-AI/Wan2.2-TI2V-5B`) | 1순위 후보 | 모델 카드 원문이 Apache 2.0이고 상업 이용·이용 지역 제한 문구가 없다. 5B로 720p·24fps, 텍스트→영상과 이미지→영상을 함께 한다. 프리비즈 대표 프레임을 첫 프레임으로 넣기에 맞는다 |
| FastVideo + FastMetal-QAD (MLX) | 실행 경로 후보 | 저장소 라이선스 Apache-2.0, Apple Silicon을 MLX 런타임으로 지원하고 Mac용 1.3B·5B·14B를 낸다. 가중치 자체의 라이선스는 채택 전에 원문 확인이 필요하다 |
| LTX-Video 계열 | 보류 | "LTX-Video Open Weights License"라는 자체 라이선스다. 매출 조건이 붙는다는 설명이 2차 자료에 있으나 원문을 확인하지 않았다. Stability 계열을 보류한 것과 같은 이유다 |
| HunyuanVideo 계열 | 기각 | Hunyuan 계열 적용 지역 규칙을 그대로 적용한다(위 3D 항목) |
| 유료 MCP(Higgsfield 등) | 기본 경로 아님 | 비용 때문에 이 저장소를 만들었다. 이 세션에서도 연결하지 않았다 |
