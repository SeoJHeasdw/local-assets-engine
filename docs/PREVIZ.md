# 프리비즈 계획 (다음 작업)

값싼 뼈대 장면으로 연출을 먼저 확정하고, 확정된 샷만 비싼 최종 생성으로 보낸다.
매번 17분짜리 생성을 돌려 보고 마음에 안 들어 다시 만드는 순서를 뒤집는 것이 목적이다.
2026-09-16에 방향을 정했고, 세부는 첫 구현에서 실측으로 정한다.

## 왜 지금인가

프리비즈에 필요한 것은 형태·크기·배치·카메라이고 텍스처 품질은 상관없다. 지금 엔진은
형태를 잘 뽑고 텍스처가 약하므로([DECISIONS](DECISIONS.md)의 복셀 해상도 한계) 강점만 쓴다.
여기서 정리되는 장면 구성·조명·카메라·에셋 정규화는 나중에 만들 3D 완성 품질 시스템에
그대로 쓰인다. 순서는 프리비즈 → 거기서 나온 개선 → 완성 품질이다.

## 만들 것

| 조각 | 내용 |
| --- | --- |
| 장면 구성 | 에셋 배치, 바닥·크기 기준. 지금 GLB가 미터 단위로 정규화돼 있어 그대로 쓴다 |
| 카메라 리그 | N개 카메라의 위치·목표·렌즈·움직임·길이를 값으로 정의 |
| 스케치 렌더 | 최종 품질이 아닌 빠른 렌더. 프레임과 짧은 영상, 깊이·윤곽 보조 출력 |
| 샷 검토 | 지금 보관함처럼 후보 샷을 보고 고르고 승인 |
| 샷 기록 | 카메라 값·타이밍·구도를 남긴다. 이것이 다음 시스템의 입력 계약이다 |

프리비즈의 진짜 산출물은 영상이 아니라 **구조화된 샷 값**이다. 최종 영상 엔진(로컬 영상
모델이든 유료 MCP든)은 그 값을 받아 만든다. 깊이·윤곽 패스는 영상 모델의 조건 입력으로 쓴다.

## 장르는 프리셋으로 흡수한다

엔진은 하나고 트레일러·강의·홍보는 샷 프리셋 묶음이다. 2D 프리셋이 프롬프트와 기본값만
다른 것과 같은 구조다. 프리셋이 정하는 값은 컷 길이, 카메라 움직임 크기, 렌즈, 구도 규칙이다.

순서는 하나씩 간다. 한 번 확인에 렌더 시간이 들어 장르 셋을 동시에 검증하면 비용이 세 배가
되고 원인도 흐려진다. 게임 트레일러부터 시작한다. 지금 엔진이 게임 소품을 만들어 입력이 이미
있고, 트레일러가 카메라 문법 중 가장 까다로워 여기서 되면 나머지는 프리셋 추가로 따라온다.
강의는 `edu/local-tts-engine`의 음성·타임라인이 있어 그다음에 붙이기 쉽다.

## 첫 구현에서 정할 것

- 산출물이 정지 프레임 스토리보드인지 움직이는 애니매틱인지
- 렌더러 선택: Workbench·EEVEE·저샘플 Cycles 중 무엇이 이 기기에서 실용적인지 실측으로 정한다
  (헤드리스 Cycles Metal은 256px 첫 렌더에 81초가 걸렸고 커널 컴파일이 대부분이었다)
- 최종 영상 경로: 로컬 오픈웨이트 영상 모델인지 유료 MCP인지. 로컬이면 한국 상업 이용
  가능 여부를 원문으로 확인한다(Hunyuan 계열 제외 규칙은 [DECISIONS](DECISIONS.md) 참고)

## 이미 있는 것을 쓴다

작업 기록·단계별 측정·승인 흐름, 한 번에 한 작업만 도는 실행 줄, Blender 헤드리스 도구,
미터 단위로 정규화된 GLB, 앱의 3D 미리보기가 모두 그대로 쓰인다. 새 레시피와 프리셋을
더하는 일이지 새 엔진을 만드는 일이 아니다.
